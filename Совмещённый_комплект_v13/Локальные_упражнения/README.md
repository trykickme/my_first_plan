# Локальные упражнения к ежедневным задачам

Всё выполняется на собственных файлах. Python-скрипты используют стандартную библиотеку, ничего не сканируют и не требуют сети. C-примеры собираются в личном Linux-стенде с доступным clang и sanitizer. Управляемый Windows 10 с Secret Net не перенастраивается; если запуск запрещён его политикой, упражнение выполняется в разрешённой личной VM или разбирается на бумаге.

Перед запуском открой терминал в этой папке. В Linux используй python3, в разрешённом Windows — py -3 вместо python3. Перед командой предскажи результат, после сохрани наблюдение и объясни причину.

## текст байты и процесс

```bash
python3 01_bytes_process.py
```

Ожидается 6 Unicode-символов и 12 байтов UTF-8, успешное обратное декодирование и два разных SHA256. PID и точные hash сравниваются с твоим запуском. Объясни, почему длины различаются и почему известный hash не удостоверяет автора файла.

## парсер и ошибки

```bash
python3 02_parser.py --help
python3 02_parser.py --self-test
python3 02_parser.py --input services.txt --output result.json
```

Первый запуск показывает справку, второй заканчивается с кодом 0. Третий сохраняет три корректных записи и ошибки строк 5, 6 и 7, возвращает код 1. Пустая строка разрешена договором и пропускается. Ошибка чтения файла возвращает код 2. Исправь три строки в собственной копии, запусти повторно и получи код 0. Добавь крайние порты 1, 0, 65535 и 65536; не заменяй проверку только положительным случаем. Затем сделай собственную версию по заметке, не подглядывая в решение.

## структура SQL и значение

```bash
python3 03_sql_binding.py
```

Обычный ввод books возвращает toy_book в обеих ветвях. Учебный SQL-подобный ввод меняет структуру конкатенированного запроса и возвращает обе записи; параметризованный запрос ищет такое буквальное значение и возвращает пустой список. База существует только в памяти процесса. Объясни, на каком шаге данные превращаются в часть программы запроса.

## граница объекта и время жизни

```bash
clang -std=c11 -g -O0 -fsanitize=address,undefined 04_bounds.c -o bounds_ok
./bounds_ok
clang -std=c11 -g -O0 -fsanitize=address,undefined -DSHOW_BUG 04_bounds.c -o bounds_bug
./bounds_bug
clang -std=c11 -g -O0 -fsanitize=address,undefined 05_lifetime.c -o lifetime_ok
./lifetime_ok
clang -std=c11 -g -O0 -fsanitize=address,undefined -DSHOW_UAF 05_lifetime.c -o lifetime_bug
./lifetime_bug
```

Если clang отсутствует, для этих двух C-примеров можно использовать gcc с теми же флагами; для libFuzzer ниже нужен clang.

Корректные варианты завершаются с кодом 0. bounds_ok читает индекс 3 и отклоняет 4. Варианты с SHOW_BUG/SHOW_UAF намеренно ошибочны: ожидаются диагностика нарушения границы/heap-use-after-free и ненулевое завершение. Формулировка, адреса и порядок сообщений зависят от сборки. Это crash собственных учебных программ. Отсутствие crash без sanitizer не превращает ошибочный доступ в допустимый.

Четыре вопроса для crash note: какой ввод или путь привёл к ошибке; какой объект и его граница нарушены; какая инструкция обращалась к нему; что доказано кроме самого crash? Не заявляй выполнение кода по одному отчёту sanitizer.

## короткий детерминированный fuzzing

Нужен clang со встроенным libFuzzer. Если его нет, читай harness и разбирай входы на бумаге; длительная установка не обязательна для зачёта задачи.

```bash
clang -std=c11 -g -O1 -fsanitize=fuzzer,address,undefined 06_fuzz_harness.c -o fuzz_ok
./fuzz_ok -runs=1000 -max_len=16
clang -std=c11 -g -O1 -fsanitize=fuzzer,address,undefined -DSHOW_BUG 06_fuzz_harness.c -o fuzz_bug
./fuzz_bug -runs=1000 -max_len=16
```

Проверенный вариант отвергает длину больше доступных данных. В ошибочном варианте проверка убрана; даже один байт с ненулевой заявленной длиной ведёт к чтению за входом. Конкретный момент обнаружения зависит от входов и сборки. Сохрани найденный файл, команду и stack trace, воспроизведи одиночным запуском ./fuzz_bug путь_к_crash_файлу, затем проверь его на fuzz_ok. Файл crash, созданный инструментом, — вход для твоего парсера, не исполняемый payload.

## Результат опыта

Заполни отдельную заметку: вопрос → предположение → контроль → наблюдение → объяснение → предел вывода → первый следующий шаг. Запуск готового решения служит разбором; самостоятельный зачёт требует воспроизвести механизм и объяснить результат без копирования.

## Дополнительные локальные опыты

Открой study_lab.py и native_lab.c. Параметры Python и C сверяй с RU01 и RU02. Для study_lab.py доступны 13 подкоманд; полный контрольный вывод находится в Ожидаемые_результаты.md. Каждая команда вида python3 study_lab.py bytes выбирает самостоятельный локальный опыт. На Windows при установленном launcher используй py -3 вместо python3.

```bash
python3 study_lab.py --help
cc -std=c11 -Wall -Wextra -O0 -g native_lab.c -o native_lab
./native_lab ABC
```

Ожидаются sum=5, bytes=78 56 34 12 на x86, accepted=1 и count=4. Аргументы ABD и AB дают accepted=0. Это собственный исправный бинарник для статического и динамического анализа. Назначение флагов сборки сверяй с RU02 и локальной справкой компилятора.
